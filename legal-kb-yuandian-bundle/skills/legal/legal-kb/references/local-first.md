# Legal KB Local-First

适用场景：
- 用户问法规、法条、案例、实务材料是否已在本地库
- 需要把检索和补库做成闭环

## 固定前提
- 唯一主库：`~/Documents/知识库`
- 缺口清单：`~/Documents/知识库/gap-log.md`
- 不再创建平行库、镜像库、展示库

## 核心原则
1. 先查本地，后查外部。
2. 元典 API 只做权威补检，不做默认主搜。
3. 付费库下载文件是补库来源，不是主检索入口。
4. 本次发现高价值缺口，就登记 `gap-log.md`。
5. 元典不可用、积分不足或明显不值，就立刻换路由，不死磕。

## 标准步骤
### A. 本地检索
1. 搜索 `~/Documents/知识库`
2. 优先看 `raw/notes/`、`wiki/sources/`、已有专题或索引条目
3. 若本地已足够回答：直接回答，并标注来自本地
4. 若本地已命中且用户只是要答案，到这里就停；不要为了显得勤奋再去外部乱搜

### B. 外部补检
4. 若本地不够，再决定外部补检来源：
   - 权威法条/案例补检 → 元典 API
   - 官方正文/公开权威来源 → 官网/法院/政府站点
   - 用户已给下载文件 → 直接用现成材料
5. 元典可用时，只补关键条文、案例、正文缺口，不拿它当全量主搜
6. 元典报余额、积分、配额或明显不值时，立即切官网、公开网络或用户已有材料

### C. 补库闭环
7. 若外部补到了，而本地缺失或只有摘要：提醒用户提供全文或下载文件，再整理入库
8. 若这类内容以后大概率还会再问：登记 `gap-log.md`
9. 若用户明确要求直接落地：除了回答，还要把补库动作接上，不只停在口头建议
10. 如果这次补检暴露出技能边界、gap-log 规则或本地目录职责需要调整，先更新技能或文档，再继续批量动作

## gap-log 触发条件
- 本地没有，但外部补到了
- 本地只有摘要，没有完整正文
- 用户以后大概率还会再问
- 需要用户去付费库下载才能真正补齐

## 对用户的汇报
只说四件事：
1. 本地是否命中
2. 外部是否补到
3. 是否建议去付费库下载
4. 是否已记入 `gap-log.md`

示例：
- 本地未命中。
- 本地未命中。
- 已用元典补到关键条文/案例。
- 这条值得补库，建议后续提供全文或下载文件。
- 已记入 `gap-log.md`。

## 元典补充
- 优先复用现有 `prc-legal-research` 配置，不随手覆写 key。
- 返回格式已改为 `{"code": 200, "data": ...}`，不要再按 `status=success` 判断。
- 元典报余额/积分问题时，立即切本地、官网、公开网络或用户已有材料。

## 注意事项
- `legal-kb` local-first workflow 负责“先查本地、再决定是否补检、是否记 gap-log”。
- 需要把新材料正式写进主库时，转交 `legal-kb` ingest workflow。
- 需要整库巡检、修索引、收口结构时，转交 `legal-kb` maintenance workflow。
- 不要把元典 API 当无限免费搜索。
- 不要因为外部能搜到，就跳过补库提醒。
- 真正长期有用的是本地入库，不是每次在线救火。
- 发现规则变了就先改文档，再继续；别让技能文档和实际动作越跑越散。
