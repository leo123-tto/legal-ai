# Legal KB Ingest

适用场景：
- 用户丢来 PDF、Word、Markdown、纯文本
- 用户发公众号链接，希望提取正文并入库
- 用户发截图、照片、零碎实务信息，希望整理进主库
- 用户从付费法律网站手动下载材料后，要求整理入库

## 固定前提
- 唯一主库：`~/Documents/知识库`
- 不再创建平行库、镜像库、展示库
- 主库目标是法律工作知识库，不是泛资讯堆场

## 核心原则
1. 所有材料只进主库。
2. 先清洗，再归档；不把原始噪音直接塞进去。
3. 零碎但高频复用的信息，也值得入库。
4. 以复用价值决定归档位置，不搞形式主义。
5. 用户手动下载的付费库材料优先级最高。
6. OCR、截图、网页内容必须先人工整理，不允许无脑入库。
7. OCR / PDF 整理默认保留原文信息；agent 只做汇总、清洗、排版，不做默认总结。需要摘要/提炼时，等用户单独要求。

## 标准步骤
### A. 先判断材料类型
1. 先分清是：付费库文件 / PDF / Word / 网页 / 图片截图 / 零碎文本 / 企业信息
2. 判断这份材料是该保留全文、改写摘要，还是并入既有条目
3. 如果发现现有技能边界、目录职责或落库规则需要调整，先更新相关技能/文档，再继续入库；不要一边规则漂移，一边硬写材料

### B. 再提取正文
3. 付费库文件：直接读取、清洗、转 Markdown
4. PDF：先尝试本包 helper 的可直抽文字 PDF 入库；如不可直抽，再判断当前环境是否有 OCR 能力
   - 先判断是否可可靠直抽文本
   - 能稳定直抽就先直抽
   - 不可靠或混合型 PDF 需要 OCR；如果当前环境没有 OCR 能力，明确说明“需要 OCR 扩展链路”
   - 长 PDF 默认按页或小批次处理；只有当前环境支持并行 agent 且用户允许时，才拆分给并行 agent
   - 不假设同事机器已安装特定 OCR 技能或运行时
5. Word / docx：提取正文，去页眉页脚和样式噪音
6. 网页 / 公众号：优先用 `kb_ingest_helper.py ingest-url` 直抓；直抓失败、正文过短或遇到微信验证页时，再用 Firecrawl 备用路径；最后删除关注引导、广告、作者简介、阅读原文、平台页脚
7. 图片 / 截图：需要 OCR；如果当前环境有 OCR 能力则先 OCR 后清洗，如果没有则明确提示需要 OCR 扩展链路
8. 零碎文本 / 实务碎片：先判断以后会不会复用，再决定是否入库
9. 企业信息 / API 结果：保留查询时间、来源和关键信息

### C. 再清洗整理
10. 补齐标题、来源、时间、结构
11. 修正明显 OCR 错误，合并断行、碎表格、bbox 垃圾输出
12. 判断落点：`raw/notes/`、`raw/companies/`，或并入已有条目
13. 没整理干净，不入库

### D. 最后写库收尾
14. 写入主库
15. 更新 `wiki/index.md`
16. 同步补一条最小必要日志；如果这次入库改变了目录职责、落库规则或后续整理口径，立即更新相关技能文档或 `.wiki-schema.md`
17. 删除原文件和中间垃圾文件
18. 给用户简短汇报：材料类型、存放位置、是否建议补更完整版本、是否登记 `gap-log.md`

## 各来源的最小处理要求
### 1. 付费库下载文件
- 读取内容
- 清洗格式噪音
- 转为 Markdown
- 写入 `raw/notes/`

### 2. PDF
- 优先用 helper 处理可直抽文字 PDF
- 先判断可靠直抽还是页级 OCR
- 混合型 PDF 按页处理，不整本一刀切
- 长 PDF 默认逐页 / 小批次处理；并行 agent 只是可选加速手段，不是必需能力
- 整理结构后入库

### 3. 网页 / 公众号
- 主路径：`kb_ingest_helper.py ingest-url --url <链接>`
- 备用路径：直抓失败时通过 `--prefer-firecrawl` 或自动 fallback 使用 Firecrawl
- Firecrawl 未配置时，要求用户提供正文、HTML/Markdown 文件，或先配置 Firecrawl
- 删除头尾垃圾
- 判断保留全文还是改写实务摘要

### 4. 图片 / 截图
- 需要 OCR；不假设默认安装 OCR 技能或模型
- OCR 后必须清洗整理，不能原样入库

### 5. 零碎文本 / 实务碎片
- 会复用才入库
- 能并入已有条目就并入，不能并入再新建

### 6. 企业信息 / API 结果
- API 花钱查到的结果不要浪费
- 企业档案写入 `raw/companies/`

## 清洗底线
### 网页 / 公众号
删除：关注引导、点赞转发提示、广告、作者简介、平台页脚
保留：标题、来源、日期、正文结构、核心观点、可复用结论

### OCR / 截图
- 修正明显识别错误
- 合并断行、碎表格、bbox 垃圾输出
- 默认保留原文信息，只做整理排版，不做默认总结
- 没整理干净，不要入库

## source 页强制模板
凡是需要写入 `wiki/sources/` 的来源页，必须使用统一模板，不得自由发挥：

```md
# 标题

> 来源：xxx | 处理日期：YYYY-MM-DD

## 核心内容

一段可复用摘要。不得只写“本文讨论了……相关法律问题”这类空话。

## 关键概念

- [[概念1]]
- [[概念2]]
- [[概念3]]
- [[概念4]]
- [[概念5]]

## 原文位置

`~/Documents/知识库/raw/notes/文件名.md`
```

硬规则：
1. `wiki/sources/` 页面必须同时包含 `## 核心内容`、`## 关键概念`、`## 原文位置` 三段。
2. `## 关键概念` 默认写 5 个；不足时也要尽量写满，避免空缺。
3. `## 原文位置` 必须是带反引号的绝对相对家目录路径写法（`~/Documents/知识库/...`）。
4. `## 原文位置` 指向的 raw 文件必须真实存在；不存在不得结束任务。
5. 标题不得截断；法规/案例类如使用 hash 后缀，标题末尾格式应稳定。
6. `## 核心内容` 必须是信息性摘要，禁止使用占位句、空话、套话。
7. 对纯实务提醒、现场指引、截图整理类材料，如原始 raw 不存在，先补 raw，再写 source；不能只写 source。

## 写库后的强制校验
写入或修改 `raw/notes/` 与 `wiki/sources/` 后，结束前必须核验：
1. source 文件标题、三段结构是否完整；
2. `原文位置` 是否闭合反引号；
3. `原文位置` 指向的 raw 文件是否真实存在；
4. 如更新了 `wiki/index.md`，对应链接是否指向真实文件；
5. 任何一项不通过，都不算入库完成。

## 元典 API 相关
- 元典可以补检，但不要和入库流程混成一坨
- 批量下载、积分管理、下载清单，放在专门的元典或研究技能里处理
- 这里保留一条就够：通过元典发现高价值缺口时，要提醒用户补全文并入库

## 注意事项
- `legal-kb` ingest workflow 只负责把材料清洗后写进主库，并补最小必要索引/日志。
- 发现需要整库巡检、收口、修 schema、批量治理时，转交 `legal-kb` maintenance workflow，不要在这里硬做。
- 发现需要先查本地是否已有、是否值得补库时，转交 `legal-kb` local-first workflow，不要把检索和入库混成一坨。
- 不要因为能临时回答，就跳过入库。
- 不要把网页脏数据、OCR 原始残渣直接塞进主库。
- 主库价值在于以后本地就能复用。
