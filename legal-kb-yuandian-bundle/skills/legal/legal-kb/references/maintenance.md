# Legal KB Maintenance

适用场景：
- 用户说“整理知识库”“收口一下”“巡检一下本地 wiki”“修 index / log / gap-log”
- `legal-kb` ingest workflow 已经把材料写进主库，但后续没人做结构治理
- 本地库已经跑过一轮批量入库，出现目录职责漂移、索引失真、overview 过期、schema 失真

## 固定前提
- 唯一主库：`~/Documents/知识库`
- 不再创建平行库、镜像库、展示库
- 本技能只做**知识库内部治理**，不负责重新 OCR，不负责在线检索主流程
- 高风险删除前要克制；默认先修结构、再清垃圾

## 核心目标
1. 让主库目录职责重新清楚。
2. 让 `index.md`、`log.md`、`overview.md`、`.wiki-schema.md` 说人话且彼此一致。
3. 识别 `raw/` 与 `wiki/` 是否脱节。
4. 把真正有长期复用价值的内容从“堆材料”推进到“可导航、可复用、可维护”。
5. 默认只做低风险修复；高风险合并或大批删除，先列入治理报告。

## 借鉴口径
参考 Karpathy LLM Wiki 一系项目时，只借三件事：
- 三层结构：raw → wiki → index/log/overview
- wiki 由代理维护，不靠人工慢慢补目录
- lint / maintenance 是独立动作，不和 ingest / query 混成一锅

不照搬的地方：
- 用户这套库是**法律工作主库**，不是泛个人 second brain
- 不引入 Obsidian 工作流依赖
- 不为了“漂亮 wiki”重写大量既有 raw 材料

## 目录职责基线
### 根目录
- `purpose.md`：主库目标、范围、排除项
- `gap-log.md`：本地未命中但值得补库的缺口清单
- `.wiki-schema.md`：维护规则与目录职责，不写过时幻想结构

### raw/
- 放原始或近原始材料
- 可清洗、可规范命名，但不做过度二次创作
- `raw/notes/` 可容纳法规正文、实务材料、OCR 整理稿、用户手动下载文件转 Markdown
- `raw/companies/` 放企业档案或查档结果

### wiki/
- 放可导航的二级知识层，而不是原始堆料镜像
- 当前最稳的子目录通常是 `wiki/sources/`
- `wiki/index.md`：导航，不是全量垃圾清单
- `wiki/log.md`：wiki 层批处理/治理日志，不替代根目录 `log.md`
- `wiki/overview.md`：主库当前覆盖面、结构状态、治理判断，不写空话模板

## 标准流程
### A. 先体检，不要上来乱改
1. 统计 `raw/` 与 `wiki/` 主要目录数量
2. 检查这些文件是否存在且内容仍可信：
   - `purpose.md`
   - `gap-log.md`
   - `.wiki-schema.md`
   - `wiki/index.md`
   - `wiki/log.md`
   - `wiki/overview.md`
   - 根目录 `log.md`
3. 判断 wiki 当前处于哪种状态：
   - 仅 raw 堆积
   - 已有 sources，但没有 entities/topics
   - 目录设计超前，真实内容没跟上
   - 索引与日志明显失真

### B. 明确问题分级
#### 低风险，可直接修
- 标题/说明与当前主库定位不符
- `overview.md` 仍是空模板
- `.wiki-schema.md` 目录与真实结构严重不符
- `index.md` 顶部概览过期
- `log.md` 缺最近整理记录
- 明显过程垃圾如 `.DS_Store`

#### 中风险，先谨慎修
- 重复索引项
- wiki 页面命名不统一
- `raw/` 与 `wiki/sources/` 的映射关系不清
- 应提升为专题页但还没提升的高价值材料

#### 高风险，默认只记录不硬删
- 大规模合并 `raw/notes/`
- 删除大量历史材料
- 覆盖式重写整批 `wiki/sources/`
- 迁移整个目录结构

### C. 先修四个锚点文件
#### 1. `.wiki-schema.md`
要求：
- 只写当前真实存在且准备长期维护的结构
- 去掉过时的 AI/科技综合口径、不存在的目录幻想、过时外挂说明
- 把 ingest/query/maintenance 的职责边界写清

#### 2. `purpose.md`
要求：
- 明确主库是法律工作知识库
- 说明优先材料类型、非主线内容如何降级处理

#### 3. `wiki/overview.md`
要求：
- 不能继续是“数量全 0”的空壳
- 必须写当前真实状态：raw 规模、wiki 层状态、主要覆盖面、治理结论、下一步重点

#### 4. `wiki/index.md`
要求：
- 顶部给出当前状态摘要
- 新增整理区只保留近期高价值条目
- 不把每个 raw 文件都硬塞成漂亮 wiki 页面
- 如果已经是法规目录总索引，可保留主体，但要修正头部说明与统计口径

### D. 再处理日志体系
- 根目录 `log.md`：记录主库入库、整理、治理动作
- `wiki/log.md`：记录 wiki 层批处理、索引修复、巡检结果
- 两者职责不能混
- 新做了一轮治理，就两边都补一条最小必要记录

### E. raw 与 wiki 脱节检查
至少看三件事：
1. 最近新增高价值 raw 材料是否进了 `wiki/index.md`
2. `wiki/sources/` 是否仍主要停留在旧批处理结果
3. 是否存在明显值得做专题页的材料簇（如某法院办案指引、某专题规则包）

做数量判断时，别偷懒用“`raw/notes` 文件名是否和 `wiki/sources` 同名”来估覆盖率。那口径会严重失真，因为 source 文件名可能保留旧命名，而真实映射关系写在页内 `## 原文位置`。

更稳的检查法：
- 扫描全部 `wiki/sources/` 页面
- 解析页内 `## 原文位置` 的 raw 路径
- 以该路径真实指向的 raw 文件，统计“已被 source 覆盖的 raw 数”
- 再反推“未被 source 映射的 raw 数”，作为下一阶段分级与派工底数

这一步特别适合用来判断“下一阶段是继续补 source，还是该优先做专题页”。经验上，source 页数量本身不重要，真正有用的是“有多少 raw 已被二级层真正接住”。

输出分三类：
- 已闭环
- 应补 wiki/sources
- 应提升为专题页 / 稳定条目

### E.1 用户说“下载内容还是补 source”时的默认决策
当用户把“下载内容 / 补 source”并列交给你判断时，不要马上联网下载。先做一轮本地底数判断：
1. 统计 `raw/notes`、`wiki/sources`、`wiki/topics`、已映射 raw、未映射 raw。
2. 如果未映射 raw 仍然很多（经验阈值：数百篇，或覆盖率明显低于 40%），默认优先补 source / topic，而不是继续下载；否则只会让库更胖、更乱。
3. 先按高频业务线扫描未承接 raw，例如：劳动工伤、婚姻家事、刑事辩护、建设工程、民间借贷/合同、公司责任、执行。
4. 对已有少量 source 但缺稳定 topic 的业务线，优先做“小批 3 篇 source + 1 个 topic”收口；这比单纯再补 3 篇散 source 更容易形成办案入口。
5. 选材优先级：规则主干 / 程序衔接 / 本地样本 / 高频实务操作；旧失效解释可以保留为“历史规则与旧案检索参考”，但必须在 source 里明示状态。
6. 做完后照常更新 `wiki/index.md`、`wiki/overview.md`、`.wiki-schema.md`、根目录 `log.md`、`wiki/log.md`，并复核新 source 五段模板、原文路径、topic/index wiki 链接。

只有在出现明确缺口清单、用户明确要烧积分下载、或本地高频线已基本承接时，才切到 `yuandian-batch-download` 继续扩库。

### E.5 单页修复时的三点联查
当用户只点名修一篇 `wiki/sources/` 页面时，也别只改那一页了事。至少联查这三处，不然很容易留下半截脏链路：
1. 对应 `raw/notes/` 文件名是否本身就截断、缺字、缺括号、缺“修正/修订”等关键信息
2. `wiki/sources/` 页内 `原文位置` 是否指向真实存在的 raw 文件
3. `wiki/index.md` 中该条目的标题与链接是否同步一致

处理原则：
- 如果 raw 文件名本身就是明显错误或截断，优先把 raw 改成规范文件名
- 改完 raw 后，必须同步修 `wiki/sources/` 的 `原文位置`
- 同步扫 `wiki/index.md`，把标题和链接一起改，不要只修链接不修标题
- 若实际文件存在但文件名就是历史脏数据，先以“真实存在 + 统一规范”收口，别让 source 页继续引用不存在路径

批量扫同类坏链时，优先盯这两类“确定性脏数据”：
1. `wiki/sources/` 中标题尾部缺右括号、缺“修正/修订”、hash 前少一个 `)`，且 `原文位置` 指向同样截断的 raw 文件名
2. `wiki/index.md` 中对应条目同时出现标题截断 + raw 链接截断，且能用同一 hash 在 `raw/notes/` 唯一定位到目标文件

经验规则：
- 先用 hash 在 `raw/notes/` 定位真实文件，再决定是否重命名；别只凭 source 页肉眼猜文件名
- 扫 `wiki/index.md` 坏链时，存在性校验要以主库根目录 `~/Documents/知识库` 为基准拼路径，不要误按 `wiki/` 目录去判；不然会把本来相对根目录正确的链接全错判一遍
- `wiki/index.md` 里大量 `raw/notes/2026-04-20-...` 形式链接不一定都是坏链，很多只是历史生成口径；不要全局一把替换
- 对这类带日期前缀的历史链接，第一层低风险修复只有一种：在“去掉 `YYYY-MM-DD-` 前缀后，`raw/notes/` 中真实文件存在”时，才可批量自动修
- 第一层修完后立刻重扫；如果还剩很多坏链，不要停在“需人工判断”这一步，继续做第二层高置信归一化匹配
- 第二层匹配的经验规则：
  - 先对索引文件名和 `raw/notes/` 文件名做归一化，再比较
  - 归一化至少包括：去 `20-` 前缀、视情况去日期前缀、统一中英文括号、去书名号/顿号/逗号/空格/下划线/连字符、轻量归并“解释/司法解释”、统一中文数字序号写法
  - 归一化后若唯一命中真实 raw 文件，可直接批量修 index 链接
  - 若不用归一化唯一命中，再考虑 fuzzy；fuzzy 只在“top1 分数足够高且与 top2 拉开明显差距”时才自动修
- 经验上，很多 `20-xxx` 索引坏链并不是 raw 缺失，而是 index 多了历史生成前缀；按归一化唯一命中批量修，风险低、收益高
- 仍未命中的极少数条目，再人工抽查 `wiki/sources/` 与 `raw/notes/`；常见特殊项包括简称页名（如 `279`）或专题简称（如“诉讼时效专题”）
- 对特殊项，先在 `wiki/sources/` 搜对应标题/原文位置，再回填 index；不要只凭猜测改成看起来像的 raw 文件
- 全部修完后必须再做一次全量存在性校验，目标是把 `wiki/index.md` 坏链清到 0，而不是“修了一批就算了”
- **别用过于简陋的 Markdown 链接正则做最终坏链结论。** 当链接目标文件名本身含英文括号（如 `规定(2020第二次修正).md`）时，很多 `\[[^\]]+\]\(([^)]+)\)` 一类正则会把第一个 `)` 当成链接结束，制造假阳性。对此类链接：
  - 优先用真正的 Markdown 解析器，或至少用更稳的链接提取逻辑；
  - 若脚本报坏链而肉眼看是“文件名含括号”场景，必须再按主库真实文件存在性人工复核一次；
  - 报告里要注明“脚本假阳性”与“真实坏链”区别，别把错误巡检结果写进结论。
- 只有在“raw 实际文件名错误/已被更正”这个前提成立时，才同步修 index 链接；否则先校验存在性再动手
- 对这类确定性问题，可以顺手小批量一起修：raw 文件名、source 标题、source 原文位置、index 标题、index 链接，五处一次收口

### F. 轻量治理动作
在不高风险的前提下，可直接做：
- 重写 `overview.md`
- 修 `.wiki-schema.md`
- 修 `index.md` 头部状态区
- 补 `log.md` / `wiki/log.md`
- 新建 `wiki/reports/` 并写一次治理报告
- 删除 `.DS_Store`、明显重复摘要、无意义空报告

默认不要直接做：
- 重建整个 wiki
- 批量删除 raw 正文
- 把 500+ 法规全重命名一遍

### F.5 报告目录清理口径
当用户说“清理过时报告”“报告太多”“看一下 reports”时，优先把它视为 `wiki/reports/` 的轻量治理，不要新建一套文档系统。

标准动作：
1. 先盘点 `wiki/reports` 顶层文件，列出文件名、大小、修改时间、一级标题。
2. 同时检查 `log.md`、`wiki/log.md`、`wiki/index.md`、`wiki/overview.md` 是否引用这些报告，避免移动后制造坏链。
3. 分三类处理：
   - **保留顶层**：当前控制文档、最新仪表盘、仍指导下一步批次的方案、每日健康报告。
   - **归档**：已被后续总览、专题页、控制文档覆盖的旧治理报告、小批次收口报告、阶段性覆盖率重算报告。
   - **删除**：过程 JSON、临时批次输入、可随时重算且无阅读价值的中间文件。
4. 归档默认落到 `wiki/reports/archive/YYYY-MM/原文件名`，不要直接删除 Markdown 报告，除非确认是空报告或重复垃圾。
5. 清理后同步更新：`.wiki-schema.md` 的 reports 目录职责、`wiki/overview.md` 的 active/archive 统计、根目录 `log.md`、`wiki/log.md`。
6. 最后复核三项：顶层报告数量、顶层 JSON 数量、旧报告引用坏链是否为 0。

这个场景和普通 doc pack consolidation 不同：重点不是重写主文档，而是给知识库报告层做 active / archive 分层，保持日志和 schema 不脱节。

## 文档更新纪律
1. 做一步，更新一步，不要最后一次性补账。
2. 只要发生了结构修复、规则调整、批量任务策略变化，就同步更新对应文档：
   - 根目录 `log.md`
   - `wiki/log.md`
   - 必要时更新 `wiki/reports/...`
   - 如果边界变化，立即改 `.wiki-schema.md` 或相关技能文档
3. 先写清规则，再做批量任务；不要一边规则没定，一边让批量产物到处漂。
4. agent 的重要职责之一，就是保证“文档状态”和“实际状态”别再次脱节。

## 批量任务分工

以下分工只在当前环境支持并行 agent / 子任务委派时使用。若不支持，就由当前 agent 按小批次、脚本和人工抽检执行同一套验收规则。

### 主控 agent 负责
- 制定技能边界、目录职责、页面模板、批量任务切分规则
- 先做小样本试跑，再决定是否放大批量
- 分配批次，控制每批范围与输入材料
- 做抽检、验收、回退、重派和规则修正
- 更新关键文档与治理报告

### 子任务负责
- 按固定模板批量补 `wiki/sources/`
- 按专题批量整理高价值 raw 材料
- 生成来源页、专题页、待复核清单
- 严格按给定边界执行，不擅自改 schema、索引规则、日志规则

### 默认工作顺序
1. 主控 agent 先把技能和规则捋顺。
2. 主控 agent 先做或安排小样本试跑。
3. 试跑通过后，再进入批量处理；可并行则并行，不可并行则小批次串行。
4. 主控 agent 必须保留监督和验收职责，不把批量输出直接视为完成。
5. 每完成一批，就同步更新日志和治理文档。

## 批量派工规范
### 一、什么材料升 `wiki/sources/`
满足任一条件，就可以优先升 `wiki/sources/`：
- 单篇材料本身有独立复用价值，后面还会被单独检索或引用
- 内容已经相对完整，适合做“来源页 / 整理页 / 摘要页”入口
- 该材料是某专题的重要组成件，但暂时还不足以单独升成专题页
- 新近入库、用户近期高频会问，值得先补一个二级导航入口

典型例子：
- 单篇办案指引
- 单份现场整理稿
- 单篇高价值公众号/实务文章
- 单份典型案例整理
- 单个法规/解释/规则包的整理稿

### 二、什么材料直接升专题页
满足任一条件，优先做专题页，不要只做零散 `wiki/sources/`：
- 同一主题下已经有 2-3 篇以上强相关材料，合在一起明显更有复用价值
- 用户后续更可能按“问题/专题”检索，而不是按单篇来源检索
- 材料之间需要交叉整理、去重、合并入口，单篇页会越看越散
- 已经形成明确工作场景，比如某法院办案指引、某类案件证据规则、某地区执行流程包

典型例子：
- 某法院起诉/执行/立案材料合集
- 某类案件裁判规则与实务操作包
- 某专项合规问题的法规 + 解释 + 典型案例组合

### 三、默认不要升 wiki 页的材料
以下情况先留在 `raw/notes/`，不要为了冲数量硬升：
- 明显重复、内容脏、还没清洗干净的材料
- 低复用、一次性、信息量太薄的碎片
- 只是过渡中间稿，后面会被并入更大条目
- 规则边界还没定清楚的材料

### 四、单批派工规模
#### 1. `wiki/sources/` 批量补页
- 默认每个子任务处理 3-5 篇
- 新模板第一次试跑时：每个子任务先只处理 1-2 篇
- 单批总量默认不超过 15 篇
- 超过 15 篇就拆批，不要一口气放飞

#### 2. 专题页整理
- 默认每个子任务只做 1 个专题
- 一个专题默认吃 2-6 篇高相关材料
- 如果专题材料超过 6 篇，先由主控 agent 再细分子专题或分阶段整理

#### 3. 禁止事项
- 不允许一个子任务同时混做“多个专题 + 多篇来源页”
- 不允许把几十篇 raw 材料一把塞给单个子任务
- 不允许规则还没试跑，就直接大批量铺开

### 五、派工前置检查
主控 agent 在派工前必须先确认：
1. 页面模板已定
2. 命名规范已定
3. 本批材料范围已定
4. 本批目标是“补 sources”还是“做专题页”已定
5. 验收标准已定
6. 日志/报告更新点已定
7. **已先查 `wiki/sources/` 是否已有对应页**

少一个都别急着派工。

### 五点五、查重分流规则
派工前先查 `wiki/sources/`，别看 raw 里像高价值就直接新建，不然很容易批量造重复壳。

- `wiki/sources/` **没有**对应页：可以新建
- `wiki/sources/` **已有**对应页但质量差、摘要脏、断裂严重：优先修旧
- `wiki/sources/` **已有**对应页且质量可用：不要重复新建，只决定要不要轻量补强

默认禁止：
- 不查重就直接新建 source 页
- 仅因为处理日期不同，就再造一篇同主题 source 页
- 对已有 source 页换个文件名再复制一份


### 六、`wiki/sources/` 查重与命名硬规则
#### 1. 先查重，再决定新建还是修旧
- 不能只看 raw 材料“像高价值”就直接补 source 页
- 派工前必须先查 `wiki/sources/` 是否已有同主题、同来源或高度相近页面
- 如果已有 source 页，默认转为“旧页复核 / 修订 / 去脏 / 补强”，不要再新建一个新日期页面
- 只有确认 `wiki/sources/` 没有对应页，才进入新建流程

#### 2. source 文件命名规则
- source 页文件名默认跟 raw 的日期与标题走
- 不要用“处理日期”“生成日期”新起一个 2026-04-24 之类的壳
- 如果 raw 文件本身没有日期前缀，就沿 raw 标题命名；不要为了统一好看擅自加新日期
- 命名规则一旦定了，批量任务必须显式写进任务说明，别让子任务自己发挥

#### 3. 发现重复后的处理原则
- 已错误新建重复页：优先删除重复新页，保留更稳的一页
- 旧页存在但质量差：走修旧路线，不走重建路线
- 如果旧页与新页各有可用信息，先人工抽检再决定合并，不要一把梭覆盖

### 七、主控 agent 验收规则

### 命名规范补充
对 `wiki/sources/` 的来源页，默认文件名应与对应 `raw/notes/` 文件同名，只改目录，不改文件名本体。

也就是说：
- raw 是 `raw/notes/2026-04-21-某材料.md`
- source 就应是 `wiki/sources/2026-04-21-某材料.md`

不要擅自改成“处理日期”“生成日期”命名，否则很容易把 raw/source 映射关系搞乱，后续索引、抽检、回链都会变脏。
如果确需偏离同名规则，必须先由主控 agent 明确批准，并在该批日志里写明原因。

### 六、主控 agent 验收规则
#### 1. 最低验收项
每批完成后，主控 agent 至少检查：
- 标题是否克制、准确，不装腔
- 内容是否基于原文整理，而不是瞎总结
- 是否按既定模板输出
- 是否误改了目录职责、索引规则或 schema
- 是否存在明显重复、漏材料、乱并条目
- 是否需要记入 `wiki/index.md`、`wiki/log.md`、治理报告

#### 2. 抽检比例
- 小批次（1-5 篇）：主控 agent 全检
- 中批次（6-15 篇）：至少抽检 40%，且必须覆盖每个子任务的输出
- 专题页：默认全检

#### 3. 打回条件
出现任一情况，直接打回重做：
- 脱离原文乱总结
- 模板不一致
- 专题边界乱了
- 单篇该升 source 却硬合进专题，或反过来
- 擅自改 schema、索引、日志规则
- 漏掉关键材料
- 处理日期、文件命名、来源字段出现漂移，和既定规则不一致

### 六点五、并行子任务试跑经验补充
在 `wiki/sources/` 修旧任务里，并行子任务通常能完成“只读 raw、只写 wiki”的边界执行，但有一个高频脏化点：**处理日期和来源字段容易漂移**。

已验证的经验：
- 同专题、同模板、每个子任务一次只给 1 篇，成功率最高
- 子任务可能沿手头上下文或当前日期，误把 `处理日期` 改成当天日期
- 即使文件名没漂，页内 `处理日期`、来源口径、标题尾部 hash 写法也可能轻微跑偏

因此派工时要显式写清：
- 只允许改 `wiki/sources/` 目标文件
- `raw/notes/` 只读，不得写入
- 文件名不改
- `处理日期` 按当前既定模板和同批页面口径保持一致，不得自行换成当天日期
- 输出必须维持五段模板：标题 / 来源与处理日期 / 核心内容 / 关键概念 / 原文位置

主控 agent 收口时至少做两件事：
1. 抽检每个子任务的一篇成品，看有没有日期漂移、来源字段漂移、模板变形
2. 若只是页内轻微漂移，主控 agent 直接修正；若边界失控，就整篇打回

### 七、批量派工后的收口
- 每完成一批，主控 agent 都要补最小必要日志
- 如果这一批验证了新规则，立即回写技能文档
- 如果这一批暴露出模板问题，先修模板再开下一批
- 不要一边发现问题，一边硬着头皮继续放量

### 八、`wiki/sources/` 旧页修订优先策略
当 `wiki/sources/` 已经有大量旧页，但其中不少是脏摘要、首段硬贴、双句号拼接、信息密度低的壳页时，默认不要回头大铺量补新页，优先做“专题簇修旧”。

### 八点二、薄弱主线的“两轮六页 + 一专题”高性价比打法
当用户已经明确一条正在建设的高频主线（例如公司责任、婚姻家事、刑事辩护、行政处罚），而该主线本地已有零散 raw、已有少量 source，但还没有稳定 topic 入口时，已验证一个很稳的推进模式：**两轮并行补 6 篇 source，再由主控 agent 收口成 1 个 topic**。

### 八点二点五、已成主线继续推进时的“2 修旧 + 1 新增”小批次打法
当某条主线已经有了 topic 骨架和一批可用 source，用户继续说“继续”“再跑一轮”，这时不一定还该机械补 3 篇新页。更高性价比的做法，往往是：**2 篇修旧增强 + 1 篇新增样本**。

### 八点二点六、劳动工伤线的连续补 source 选材顺序
当当前主线是劳动工伤，且用户要求“继续，连着跑，不要问”时，优先沿同一条线连续补 source，不要突然切到别的法域。已验证的稳妥推进顺序：
1. **先补规则主干**：劳动合同法实施条例、工伤保险行政案件司法解释等能直接回答高频问题的现行规则。
2. **再补程序衔接**：劳动争议调解仲裁法、劳动人事争议仲裁办案规则、仲裁诉讼衔接意见；这类材料要突出调解协议、撤回仲裁、请求转换、证据衔接、自认、终局裁决。
3. **旧司法解释可入 source，但必须明示状态**：劳动争议解释、解释（二）（三）（四）等旧解释如果 raw 标注失效，source 顶部必须写“原文标注为失效，作为历史规则与旧案检索参考”，不要装成现行规则。
4. **再补样本边界**：优先权威/本地案例，如上下班途中合理时间、已到岗后离岗、三工认定、加班费举证、违法解除、强制清算中职工经济补偿等。
5. **遇到重复 raw 先选更干净的一份**：同一案例或规则有 `_1`、乱码标题、不同批次重复文件时，只为较规范、标题不乱码的一份建 source；另一份先记录为重复候选，不要同时造两个 source 壳。
6. **topic 分组建议**：规则主干 / 劳动争议司法解释与历史口径 / 仲裁诉讼衔接 / 工伤认定与本地口径 / 实务材料与案例入口。
7. **本线下一步优先级**：当规则和旧解释已接住后，继续补江苏/无锡劳动关系认定、加班费、违法解除、三工认定案例；不要继续沉迷补旧解释。
8. **第三轮以后转向“成对样本 + 特殊保护”**：工伤方向优先用本地正反样本成对补强，例如“单位拖延申报导致超期可扣除耽误期间”配“不能证明法定延误情形则超期不予受理”；同一细问题补到正反边界后就停，不要继续堆申请期限材料。劳动争议方向优先补孕期/生育津贴、轻微违纪违法解除、比例原则/过罚相当、工会通知程序等能直接指导办案的权威案例。
9. **topic 分组随内容演进**：劳动工伤专题跑到案例层后，应从“实务材料与案例入口”里拆出“违法解除、特殊保护与经济补偿样本”一组；工伤本地样本则继续挂在“工伤认定与本地口径”下，避免案例入口变成一锅粥。
10. **第四轮补工资社保和程序底座**：劳动工伤线已有规则、旧解释、工伤样本、违法解除样本后，下一轮不要继续堆同类工伤期限或程序裁定，优先补工资支付暂行规定、最低工资规定、社会保险法等“工资社保底座”，再接 2-3 篇劳动报酬/二倍工资/加班费程序或实体样本。
11. **程序样本够用后切实体判决**：仲裁前置、撤诉后再仲裁、二倍工资程序裁定这类材料补 1-2 篇足够；继续劳动工伤线时，优先找江苏/无锡劳动关系认定、加班费举证、未签合同二倍工资的实体判决样本。程序裁定继续堆就是灌水，别自我感动。
12. **topic 分组继续拆细**：补入工资社保后，应把劳动工伤专题从单一“实务材料与案例入口”拆成“工资、社保与劳动报酬入口”和“劳动关系、二倍工资、加班费程序样本”；这样检索时能直接按问题入口走，而不是在案例堆里翻垃圾。

适用条件：
- 当前主线已经形成基本专题入口；
- `wiki/sources/` 里已经有同主题旧页，但质量偏薄、表述偏松、模板脏或引用的是较弱 raw；
- `raw/notes/` 中还有 1-2 篇值得新接住的样本或支线材料；
- 用户要的是“继续往前推”，不是单纯冲 source 数量。

推荐结构：
1. **一篇修旧规则/程序页**：把旧壳页改成真正能回答问题的稳定入口；
2. **一篇修旧代表样本**：优先修高价值但现有摘要过薄、原始依据更完整的判例页；
3. **一篇新增支线样本**：补进当前专题还没接住、但能明显拓宽边界的材料，比如本地样本、特殊主体样本、程序变体样本。

主控 agent 收口时至少做四件事：
- 明确在日志/报告里区分“修旧”与“新增”，不要都写成“新增 source”；
- 把修旧后的页面重新回挂到 topic，必要时改专题里的说明文字；
- 重算真实底数与 source 映射数，别因为只修旧就忘了数字同步；
- 若修旧页对应的 raw 有更完整版本、重复版本或旧命名版本，至少人工判断一次，不要让 source 长期挂在较差底稿上。

经验判断：
- 对已经跑起来的主线，这个模式往往比继续“3 篇全新 source”更值，因为它能同时解决**入口质量**和**边界补强**两个问题；
- 这仍属于 `legal-kb` maintenance workflow 的主控 agent 收口范畴，不需要单独再造新技能。

推荐结构：
- **第一轮 3 篇**：
  1. 一篇规则/纪要/解释主干材料；
  2. 一篇权威案例或能定边界的代表样本；
  3. 一篇地方样本或程序衔接样本。
- **第二轮 3 篇**：
  1. 一篇实务操作/流程型材料；
  2. 一篇本地样本（优先江苏/无锡）；
  3. 一篇补短板材料，用来把责任边界、程序入口或地方特色补完整。

这个模式的适用条件：
- 用户说“直接跑”“不用问我”“多跑两轮”；
- 主线已经确定，不需要再做方向讨论；
- 当前更缺的是入口和判断骨架，而不是海量铺料；
- 适合公司责任、婚家、刑事辩护这类可以明显拆成“规则 + 样本 + 操作”三层的线。

主控 agent 收口动作固定四件事：
1. 全检 6 篇 source，统一五段模板与 `原文位置`；
2. 新建或扩写 1 个 topic，把 6 篇材料按“规则主干 / 样本边界 / 实操入口”分组；
3. 同步更新 `wiki/index.md`、`wiki/overview.md`、`log.md`、`wiki/log.md`、`wiki/reports/...`；
4. 结束前重算真实底数与 source 映射数，别把 topic 建好了、数字还停在上一轮。

经验判断：
- 对薄弱主线，先做这“两轮六页 + 一专题”，通常比一口气撒 10+ 篇 source 更稳，也更容易形成真正可用的办案入口；
- 这个打法本质仍属于 `legal-kb` maintenance workflow 的“内容建设型收口”，不是另一个新技能。

### 八点五、全量体检的最小巡检脚本思路
当用户要求“继续扫”“批量清一下 sources”时，先做一轮全量结构巡检，再决定逐页修，别凭感觉翻文件。

最小巡检项就三组：
1. 标题行：
   - 是否以 `# ` 开头
   - 是否存在明显括号不平衡、hash 前缺右括号、标题尾截断
2. `原文位置`：
   - 是否存在 `## 原文位置`
   - 是否是闭合反引号路径
   - 展开 `~` 后是否真的指向存在的 `raw/notes/` 文件
3. 模板完整度：
   - 是否都有 `## 核心内容` / `## 关键概念` / `## 原文位置`
   - `核心内容` 是否过短到明显只是占位句

经验上，这一轮巡检足够快，而且能先把“结构问题”和“内容质量问题”分开，不会一上来就掉进逐页手工翻修。

### 八点六、`wiki/sources/` 自动修复优先级
巡检后，先修这几类低风险问题：
1. 缺 `## 关键概念`
   - 直接补 4-5 个贴切概念即可，别为了凑数胡塞泛词
2. `原文位置` 缺失或未闭合
   - 先查 raw 是否存在；存在就回填规范路径
3. source 页不是统一模板，但正文其实可复用
   - 直接改写成统一五段模板，不必保留旧的自由散文结构
4. `核心内容` 明显是占位句
   - 基于 raw 原文重写成一段可检索、可判断用途的摘要

### 八点七、source 缺 raw 时的处理口径
有些 source 页不是法规，而是实务提醒、现场整理、公众号短文。这类页如果结构有价值但 raw 缺失，不要只把 source 判成坏页就停下。

可复用的低风险做法：
- 若 source 正文本身已是较完整整理稿，可直接落一个同主题 raw 文件到 `raw/notes/`
- raw 命名默认跟 source 文件名走；不要另造花哨名字
- 落完 raw 后，再把 source 收口成统一模板，并把 `原文位置` 指过去

这个做法尤其适合：
- 实务避坑提醒
- 现场公告整理
- 微信 / 腾讯调证等流程型经验页

### 八点八、修完后一定重跑一次全量巡检
别修完就自我感动。至少再跑一次全量检查，目标是把这三项清到 0：
- 标题结构异常
- `原文位置` 坏链 / 未闭合
- 模板缺段或明显占位摘要

### 八点八点五、`原文位置` 脏链批量修复实操口径
当用户明确要求“先修 source 脏链”“先把原文位置清掉”时，不要逐页手改，直接按下面顺序批量收口：

1. **先全量扫描 `wiki/sources/*.md`**
   - 只抓 `## 原文位置` 一项
   - 区分三类问题：
     - 缺 `原文位置`
     - 有反引号但路径不存在
     - 路径存在但写法不统一（相对路径、`/Users/...` 绝对路径、旧文件名）

2. **先统一路径写法**
   - `wiki/sources` 一律收口成：
     - ``~/Documents/知识库/raw/notes/文件名.md``
   - 不再混用 `raw/notes/...` 相对路径或 `/Users/...` 绝对路径

3. **回链匹配按三层优先级走**
   - 第一层：`source` 文件名与 `raw/notes` 文件名同名，直接命中
   - 第二层：若文件名带 hash，优先用 hash 在 `raw/notes` 唯一定位真实文件
   - 第三层：若仍未命中，再对 `source` 文件名 / 标题与 `raw` 文件名 / 标题做归一化匹配，唯一命中才自动修

4. **归一化匹配最低规则**
   - 去日期前缀（如 `2026-04-13-`）
   - 去 `[国法]` 这类前缀壳
   - 统一中英文括号
   - 去 hash 后缀、空格、下划线、连字符、常见标点
   - 对法规类标题，允许“全文 / 修正 / 修订 / 解释”等轻度口径差异后再比

5. **两个高频例外要单独盯**
   - `source` 文件名是旧批量生成日期名，真实 raw 是后来的规范标题名
   - `source` 标题是法规正式标题，但 raw 落的是“全文”或“通知”版本；这类要以真实文件存在为准，不要硬按标题字面死配

6. **修完必须再全量校验一次**
   - 目标不是“修掉一批”，而是把 `原文位置` 异常清到 0
   - 结束前至少输出：修复数量、剩余数量、剩余样例；若剩余不为 0，就继续收口，不要假装完成

### 八点九、和 ingest 技能的闭环约束
`legal-kb` maintenance workflow 不是独立口径，必须和 `legal-kb` ingest workflow 使用同一套 source 规范。巡检和验收时，把下面这些当成硬规则，而不是“建议”：
1. 任何 `wiki/sources/` 页都必须符合统一五段模板：标题 / 来源与处理日期 / 核心内容 / 关键概念 / 原文位置。
2. `## 原文位置` 指向的 raw 文件必须真实存在；若 source 有价值但 raw 缺失，优先补 raw，再修 source，不允许只留下 source 空壳。
3. `## 核心内容` 不得是占位句、空话或“本文讨论了……”式摘要；发现这种页，maintenance 应直接列为待修，而不是视为“已有页面”。
4. 对实务提醒、截图整理、现场指引类材料，如果 source 可复用但 raw 不存在，maintenance 可按低风险规则补一个同主题 raw 文件，再把 source 收口到统一模板。
5. 当 maintenance 发现结构性脏数据是 ingest 规则缺失造成的，应立即反向 patch `legal-kb` ingest workflow，不要只修数据不修规则。

### 八点十、source 巡检合格线
执行 source 层巡检后，至少输出这四个数：
- 标题异常数
- 原文位置异常数
- 模板缺段数
- 占位式摘要数

如果四项任一不为 0，就不应把该轮维护标记为“完成”；最多只能标记为“已发现并部分修复”。

### 八点十一、每日轻量体检任务口径
当用户要求“要不要做每日定时任务”或希望知识库长期稳定运行时，推荐只做每日轻量体检，不做自动大修。

已验证的稳妥边界：
- 定时任务只巡检、记录、汇报；不批量重命名、不批量删除、不重建 wiki、不递归创建新定时任务。
- 默认时间可设为每天 23:30，避免打断白天工作。
- 输出落到 `wiki/reports/daily-kb-health.md`，保留最近 30 天记录即可。
- 最终汇报要短：正常时只报核心数字；异常时列异常类型和少量样例路径。

每日最小巡检项：
1. `raw/notes` 数量
2. `wiki/sources` 数量
3. `wiki/topics` 数量
4. `wiki/reports` 数量
5. 解析 `wiki/sources/*.md` 内 `## 原文位置`，统计已映射 raw 与未映射 raw
6. source 标题异常数
7. source 原文位置异常 / 坏链数
8. source 模板缺段数（`## 核心内容` / `## 关键概念` / `## 原文位置`）
9. source 占位式摘要数
10. `wiki/index.md` markdown 文件链接坏链数

创建 cronjob 时的建议配置：
- `skills`: [`legal-kb` maintenance workflow]
- `enabled_toolsets`: [`terminal`, `file`]
- `workdir`: 用户主目录
- `deliver`: 当前会话 / origin
- prompt 必须写明：只做轻量巡检与最小记录；发现重大异常只报告，不擅自修复。

#### 1. 怎么选修旧批次
优先顺序：
- 同一批日期、同一专题下的一串高复用页面
- 用户近期正在用、后续大概率还会继续检索的材料
- 旧页明显只有首段摘抄、拼接感重、关键词乱飘的页面
- 法规正文页、法规壳页、作者专题页、学术解释页可以成组收口时，优先整组处理

典型专题簇：
- 执行 / 执行异议 / 执行异议之诉
- 民间借贷事实认定 / 裁判规则 / 典型案例 / 开庭提问清单

对“程序型专题簇”（尤其执行线）有个很实用的补页顺序，别只盯着法规正文和零散文章：
1. **程序入口型材料**：例如执行监督程序指南、复议/异议受理边界规则，先解决“这事到底走哪条程序”；
2. **类型化裁判指引**：例如把借名买房、以房抵债、租赁权、追加被执行人拆开讲的地方高院裁判指引，先解决“同属一类案件时怎么分型”；
3. **反误区案例**：例如“先查封不当然优先受偿”这类能直接纠正常见办案误解的案例页，先解决“哪些口号其实是错的”。

经验上，这三类材料一接进去，专题页的办案可用度会明显高于单纯再补一篇总论文章。

#### 2. 修旧时的 source 模板
默认保持稳定五段：
- 标题
- 来源与处理日期
- 核心内容
- 关键概念
- 原文位置

其中“核心内容”写法要求：
- 基于原文整理，不直接糊原文首段
- 主控 agent 只做汇总、清洗、排版，不默认拔高成论文式总结
- 说明这份材料的用途、适用场景、核心争点或规则边界
- 能区分“法规正文页 / 法规壳页 / 索引页 / 学术文章页 / 实务指引页”的不同定位

#### 3. 修旧而不是重建的触发条件
满足任一项，优先修旧：
- 文件名和 raw 映射关系没问题，只是内容质量差
- 旧页已有稳定入口价值，删了反而会把索引打乱
- 同主题下已经存在多页，需要统一口径，而不是另起新壳

#### 4. 专题簇推进顺序
- 先拿 3-5 篇做一轮小样本
- 主控 agent 抽检通过后，再沿相邻页继续扫
- 一轮只清一个专题簇，别执行和民间借贷混着撒网
- 如果专题内已形成“法规 + 文章 + 索引 +案例/规则包”，优先把这一簇拉成线

#### 5. 进度文档
进入连续修旧状态后，建议在用户指定文档持续记进度，至少写清：
- 本轮修了哪些页
- 为什么这批优先
- 当前判断的下一批最值方向

对用户只汇报四件事：
1. 我判断这个库现在是什么状态
2. 我这轮已经修了什么
3. 哪些问题我故意没乱动
4. 下一步最值的动作是什么

#### 6. 分阶段推进时的“控制文档”做法
当用户明确要求“以后随时读文档就能接着干”，不要只把状态散落在聊天和日志里。主控 agent 应额外维护一份用户指定的控制文档（例如桌面计划文档），把它当成本阶段唯一驾驶舱。

#### 6.2、模型切换 / 低成本接手交接方案
当用户说“先做方案，之后换另一个模型继续”“现在模型贵，给下一个模型交接”“让 GPT-5.4/低成本模型接着跑”时，maintenance 应把这当成正式治理产物，而不是只在聊天里口头说。

推荐做法：
1. 先完成一次最小体检：真实底数、source 四项质量、index 坏链、当前 topic/report 状态、明显过程文件。
2. 把方案落到 `wiki/reports/YYYY-MM-DD-模型或handoff-plan.md`，不要丢桌面。
3. 方案至少包含：当前真实状态、技能判断、问题清单、下一阶段批次、验收标准、禁止事项、给下一个模型的可复制指令。
4. 批次设计要从“先收口仪表盘”开始，再进入内容建设；不要让接手模型一上来就批量造 source。
5. 给下一个模型的指令必须写明：先加载哪些技能、先读哪份交接文档、主库路径、先做哪个 Batch、哪些动作只报告不删除。
6. 最终给用户的回复只给结论和可复制指令，不倒过程文件细节。

这个场景本质仍属于 `legal-kb` maintenance workflow，不需要另建“handoff”技能。

#### 6.5、用户只说“继续”时的自主续跑口径
当用户已经明确了当前主线（例如执行专题、公司责任专题），后续只说“继续”“继续跑”“你自己规划再跑几轮”，主控 agent 不要再来回请示。直接按当前主线自主规划 2-3 个连续小批次，并在每批结束后同步更新索引、专题页、日志和治理报告。

实操规则：
1. **先沿当前主线补完边界**，不要一听“继续”就换大主题。比如执行线已补到拒执、房屋排除执行，就优先顺着恢复执行、程序救济、带租拍卖继续补，而不是突然跳去别的法域。
2. **每一轮仍按小批处理**：默认每轮 3 篇左右；当前环境支持并行 agent 时，每个子任务只做 1 篇 source，并由主控 agent 统一验收。
3. **如果预设子主题候选不足，不要硬凑。** 先查 raw/source 现状；若发现该子主题缺少足够高价值 raw，就改派到同一主线下相邻的高价值子簇，例如从“承租人租赁权”切到“恢复执行边界”或“公司清算责任”，但必须在日志/报告里写明 reroute 原因。
4. **连续多轮时，至少保持一条清晰叙事线**：例如“程序边界 → 责任边界 → 反误区案例”，不要三轮各补一堆彼此无关的散点。
5. **结束前做总收口**：除每轮日志外，再补一份总报告，概括这几轮补了哪些簇、哪些故意没动、下一步最值的方向。
6. 这类“继续跑几轮”的场景，本质上仍属于 `legal-kb` maintenance workflow，不需要另造新技能。

控制文档至少写这几块：
- 当前真实底数（raw / sources / topics / 已映射 raw / 未映射 raw）
- 当前主线与当前批次（例如 Batch 0 / Batch 1）
- 主控 agent / 子任务分工与验收规则
- 本批正式产物清单
- 当前进度记录
- 下一步动作

执行纪律：
1. 先写方案和批次，再进入批量处理；别边跑边临时想。
2. 每完成一批，就立刻把控制文档改到最新状态；不要等全部做完再补账。
3. 主库正式日志（`log.md` / `wiki/log.md`）照常更新，但它们不是控制文档替代品。
4. 下次继续时，优先先读控制文档最后的“当前进度记录 / 下一步”，再决定接着跑哪一批。

#### 7. 主控 agent + 子任务批次模式的实操口径
当任务进入“继续建设知识库内容”阶段，推荐固定采用下面的批次模式：
- 主控 agent 负责：定专题、定范围、先查重、写任务卡、验收、收口、更新控制文档与日志
- 子任务负责：单批 source、新专题页、分级报告等边界清楚的产物

实操经验：
1. 第一批不要贪多，先处理单个明确产物，例如“1 份分级报告 / 1 个专题页 / 1 篇 source”。
2. 主控 agent 必须全检首批产物，不要把批量输出直接视为完成。
3. 子任务高频问题不是瞎编，而是模板漂移、标题格式漂移、链接口径漂移；主控 agent 要重点抓这三类。
4. 一旦发现某个子任务产物只是轻微漂移，主控 agent 直接手工收口，不必整批打回；但如果边界跑偏，再打回重做。
5. 小批跑通后，再进入下一批增量，例如“专题页跑通后，继续补 3 篇高频 source，再回挂专题页”。
6. 每批完成后，必须同步更新：控制文档、`wiki/index.md`、`wiki/overview.md`、`log.md`、`wiki/log.md`（至少更新其中受影响的部分）。

#### 7.4、用户明确要求“全自动补 N 篇 source 再停”的批量模式
当用户明确说“全自动”“不要问我”“补完 N 篇 source 再停”“我去睡觉，不要打扰”时，这属于例外的大批量自动补 source 场景；不要再按普通 3-5 篇小批反复打断用户，也不要中途汇报。

适用条件：
- 用户给了明确数量上限（如 50 篇），并明确授权自主决策；
- 当前 source 结构健康，坏链/模板缺段/占位摘要已清零或可先快速清零；
- raw 未映射仍然很多，继续补 source 比继续下载更值；
- 本轮只新增 source 和必要报告/日志/索引，不做高风险删除、重命名、合并。

推荐流程：
1. 先用脚本盘点：`raw/notes` 总数、`wiki/sources` 总数、已映射 raw、未映射 raw、覆盖率、source 四项质量。
2. 从未映射 raw 中按高频业务线打分选材：执行、公司责任、合同借贷、建设工程、行政、刑事、婚姻家事、劳动工伤；优先规则主干、权威案例、本地样本、程序入口，过滤培训/征文/过程文档/极薄纯程序件。
3. 若用户没有指定领域，按当前库短板和律师高频需求分配配额；实测 50 篇可用配额示例：执行 9、公司责任 9、合同借贷 9、建设工程 7、行政 6、刑事 5、婚姻家事 3、劳动工伤 2。
4. 大批量时优先用脚本直接生成 source，避免大量重复派工成本。仍必须保持五段模板：标题 / 来源与处理日期 / 核心内容 / 关键概念 / 原文位置。
5. source 文件名默认与 raw 同名，只从 `raw/notes/文件名.md` 映射到 `wiki/sources/文件名.md`；不要用处理日期造新壳。
6. 生成一个批次报告：`wiki/reports/YYYY-MM-DD-source-batch-N.md`，记录分布和清单；报告是治理记录，不是让用户读过程垃圾。
7. 同步更新 `wiki/index.md` 顶部状态和少量代表条目、`wiki/overview.md` 底数和覆盖率、根目录 `log.md`、`wiki/log.md`。
8. 最后全量巡检，必须确认：标题异常 0、模板缺段 0、原文位置坏链 0、占位式摘要 0、批次报告条目数等于用户指定 N。
9. 清理临时脚本；最终只简短汇报完成数字和质量指标。

注意：这种模式是“有明确数量上限的大批量 source 补页”，不是日常无限自动改库。到达用户指定数量就停，别自作主张继续跑。

#### 7.5、并行子任务补单篇 source 的高成功率任务卡
当一批任务本质上只是“把 3-5 篇彼此独立的 raw 升成 source”，不要让子任务自由发挥成专题整理。更稳的派法是：
- 先确认当前环境是否支持并行 agent；不支持时就按同一规则小批次串行处理。
- 每个子任务 **只处理 1 篇** raw，对应 **只写 1 个** `wiki/sources/` 文件；
- 任务卡里直接写死：目标 raw 路径、目标 source 路径、统一五段模板、固定处理日期；
- 明确禁止改 `raw/notes/`、`wiki/index.md`、`wiki/log.md`、`wiki/topics/`、`wiki/reports/`；
- 要求子任务在总结里回报**写入的绝对路径**，方便主控 agent 复核；
- 主控 agent 收口时必须逐篇检查四件事：模板三段是否完整、`原文位置` 是否闭合且使用反引号包裹、raw 是否真实存在、索引/专题回挂后是否能命中真实文件。
- 并行输出可能漏掉 `原文位置` 外层反引号；验收脚本必须抓这一项，发现后由主控 agent 直接补反引号即可。
- 子任务总结只当线索，不当验收结论；主控 agent 必须读回写入文件，核对五段模板、来源字段、处理日期、`原文位置` 和是否误改其他文件。
- 子任务写出的 `## 关键概念` 可能是项目符号解释而不是 `[[概念]]` 串；只要模板完整、概念贴切、检索价值明确，可接受，不必为形式洁癖返工。但同批次若要高度统一，主控 agent 可轻量收口。

这个模式特别适合法律知识库的单篇案例卡片和规则卡片：执行线案例、劳动工伤案例、公司责任案例、单篇法规/解释/审理指南等，彼此独立、复用价值高、适合并行，不必硬捏成一个大专题再派工。

再补一条已经实测有效的选材顺序，尤其适合执行异议之诉 / 房屋排除执行这类“同题材不同边界”的小批次：
1. 一篇**正向成立型**材料：例如在什么条件下可以主张排除执行；
2. 一篇**反向驳回型**材料：例如长期未过户、未尽注意义务、仅有实际占有但仍不支持排除执行；
3. 一篇**程序滥用/刑责衔接型**材料：例如虚构租赁关系、借执行异议或异议之诉阻却拍卖，最终落到拒执罪既遂边界。

这样一批 3 篇卡片一落地，专题页马上就有“能成立 / 不能成立 / 乱用程序会出什么事”三层判断，不容易只堆单边观点。
## 注意事项
- 这个技能是“收口”，不是“再发明一个系统”
- 不要拿国外 wiki skill 的目录直接硬套用户现有主库
- 用户不想看一堆过程文件路径；最终汇报说结果，不倒垃圾
- 如果在治理中发现 `legal-kb` ingest workflow 或 `legal-kb` local-first workflow 的边界描述过时，顺手 patch 它们
